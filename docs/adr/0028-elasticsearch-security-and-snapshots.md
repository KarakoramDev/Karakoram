# 0028 — Elasticsearch security and native S3 snapshots

Status: Accepted

## Context

Security feature-state restore can replace native and built-in credentials. Recovery needs a control identity independent of that state. Native snapshots preserve Elasticsearch data and feature states; live filesystem archives do not provide a supported database recovery mechanism. S3 compatibility must include Elasticsearch's concurrent repository semantics, not just object upload/download ([file realm](https://www.elastic.co/docs/deploy-manage/users-roles/cluster-or-deployment-auth/file-based), [snapshots](https://www.elastic.co/docs/deploy-manage/tools/snapshot-and-restore), [S3 repositories](https://www.elastic.co/docs/deploy-manage/tools/snapshot-and-restore/s3-repository)).

## Decision

Always enable security and require HTTP/transport TLS under the cluster CA; accept only `spec.tls.mode: requireTLS`. Disable automatic security setup, not authentication. Generate per-node HTTP and transport leaves, require transport client authentication and use CA-based transport certificate verification. Support self-generated or user-provided signing CA material through the existing protected secret model. Reserve discovery, identities, security/TLS and repository client settings from user overrides ([security settings](https://www.elastic.co/docs/reference/elasticsearch/configuration-reference/security-settings)).

Render consistent file-realm accounts on every Elasticsearch node: `karakoram` with superuser rights for control/recovery, and `karakoram-monitor` with cluster/index monitoring only. Use the native realm for application users. Set `elastic` as the human administrative superuser and reveal it only through the separately authorized credentials endpoint. Kibana uses an API-created `elastic/kibana` service-account token, not the human password. Logstash/APM use scoped writer users over their supported log/metric/trace patterns; APM intake uses a separate secret token and optionally API keys ([service accounts](https://www.elastic.co/docs/deploy-manage/users-roles/cluster-or-deployment-auth/service-accounts), [Logstash security](https://www.elastic.co/docs/reference/logstash/secure-connection), [APM authorization](https://www.elastic.co/docs/solutions/observability/apm/apm-server/apm-agent-authorization)). Protect reserved users/roles from application CRUD.

Rotate leaf certificates through watched PEM files under the existing CA without Elasticsearch restart. Rotate `elastic`, Kibana token, Logstash/APM writer passwords and APM intake token through durable operations; re-ensure Elasticsearch objects and republish/restart affected stateless components. Retain the three cluster-lifetime Kibana encryption keys. Rotation of credentials or leaves is not CA rotation ([secure settings and reload](https://www.elastic.co/docs/deploy-manage/security/secure-settings)).

Map every referenced BackupStorage to a stable named S3 client. Put endpoint URL, signing region and path-style access in node settings; changing the storage/client set requires a rolling restart. Put access/secret keys in every node's keystore; credential changes use `_nodes/reload_secure_settings`, without restarting. Register one verified repository per storage with a base path derived from storage prefix, namespace, cluster name and immutable cluster UID. Allow one writer only; restore destinations register the source path read-only ([S3 settings](https://www.elastic.co/docs/reference/elasticsearch/configuration-reference/s3-repository-settings)).

Backups use type `snapshot` and include all indices/data streams, global state and feature states. Poll native snapshot completion; partial/failed snapshots are not successful recovery bases. Karakoram's existing scheduler owns schedules and count retention uniformly across engines; do not create SLM policies. Delete snapshots through the native repository API. Record immutable provenance as `Backup.location: s3://<bucket>/<base_path>?repository=<repo>#<snapshot>`; this is a repository/snapshot reference, not a per-snapshot blob prefix.

In-place restore is destructive and checkpointed: stop all Kibana/Logstash/APM services at the platform level and observe completion; temporarily set transient `action.destructive_requires_name: false`; delete all data streams (including hidden streams) and non-system indices (including hidden and closed indices); restore the snapshot including global state, aliases and feature states; wait for recovery; reset the temporary setting; re-ensure managed credentials through the unaffected file-realm identity; republish current configuration and restart the services. System indices are restored by feature state, not blanket deletion. External application writers must be quiesced separately. Restored application users, API keys, templates and persistent cluster settings are snapshot state, not automatically reconciled application intent ([restore semantics](https://www.elastic.co/docs/deploy-manage/tools/snapshot-and-restore/restore-snapshot)).

For a new cluster from backup, `spec.dataSource` requires a source cluster that still exists and uses Elasticsearch. First form the destination, register the source repository read-only, restore, ensure destination system credentials, then register its own unique writable repository. For a retained backup of a deleted source, create a destination without `dataSource` and use an explicit restore operation referencing the retained backup's original source cluster/namespace. Reject newer-to-older restore and incompatible snapshot/index versions; a target at most one major ahead is a policy bound, not proof every source index is compatible. Snapshots omit node configuration, CA/private keys, keystores and repository registrations; retain protected control-plane state and storage configuration as well as S3 objects.

With `keepBackups: false`, cleanup deletes snapshots in owned writable repositories through Elasticsearch before deleting infrastructure. Read-only source repositories are never deleted. If Elasticsearch is unreachable, record a `SnapshotsRetained` warning and continue infrastructure deletion, leaving snapshots in object storage. With `keepBackups: true`, preserve them explicitly.

A retained backup of a fully deleted cluster can be deleted directly only when it is the sole snapshot in its retired repository path and that path has no active writer. Snapshots share blobs; otherwise register the repository in another Elasticsearch cluster and delete through its native snapshot API, rather than deleting individual object keys.

S3 compatibility requires successful repository `_verify` and `_analyze` against the actual destination, not only ordinary object upload/download. Elasticsearch 9.3+ requires S3 conditional writes for its register implementation. Do not enable an unsafe compatibility workaround when storage fails that contract; investigate failures. Repository checks do not establish durability or production-scale performance ([analysis API](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-snapshot-repository-analyze), [conditional writes](https://www.elastic.co/docs/deploy-manage/tools/snapshot-and-restore/s3-repository), [Zerops Object Storage](https://docs.zerops.io/object-storage/overview)).

## Consequences

The file-realm control identity is deliberately powerful and must remain encrypted and protected. Monitoring and ingestion identities limit routine privilege reuse, not platform-administrator trust. Restores replace security/global state and interrupt stack services; successful recovery also requires authentication and application-data checks. New storage settings can trigger rolling maintenance. Repository isolation and single-writer ownership are correctness requirements. Scheduler availability depends on the control plane; ILM is live-data lifecycle, not backup retention.

## Alternatives considered

- **Only native/built-in control credentials:** snapshot security restore can invalidate the credential required to finish recovery.
- **Security or TLS disabled for development:** creates a different trust model and incompatible component wiring; rejected.
- **Live Local Storage archives:** not Elasticsearch-native, application-consistent snapshots.
- **SLM scheduling:** valid Elastic feature, but would introduce a second scheduler/retention owner.
- **Shared writable source repository for clones or unsafe S3 fallback:** risks repository corruption rather than preserving recovery correctness.
