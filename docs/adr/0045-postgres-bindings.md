# 0045 — PostgreSQL bindings for dependent services

Status: Accepted

## Context

Identity providers, workflow engines, secret stores and similar services need a [PostgreSQL](https://www.postgresql.org) database. Embedding a private database in each service duplicates HA, backups and upgrades; asking operators to create roles by hand loses credential rotation and lets a database be deleted underneath its consumers.

## Decision

### Model

A **binding** links one consumer (another Karakoram cluster, identified by engine driver kind, namespace and name) to one source cluster of the `postgres` engine driver. It is created by the consumer's engine driver through the in-process `internal/pgbinding.Service` during reconciliation and released during the consumer's deletion; it is idempotent per consumer/source pair. Bindings are persisted in their own table keyed by source cluster incarnation (namespace, name and UID), so a re-created source of the same name never inherits bindings.

`Ensure` creates on the source, through the native access path ([ADR 0034](0034-postgres-engine.md)) with its sealed intents and receipts:

- one login role `kb_<hash>` with `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`, no memberships and an explicit connection limit;
- one to eight databases owned by that role, with the role owning their `public` schema;
- requested extensions, which must be in the source's available set ([ADR 0044](0044-postgres-profiles.md)).

The `kb_` prefix is reserved: binding roles are routable through the source proxy but cannot be modified through the access API. The password is generated by the control plane and sealed under the source cluster; the binding exposes only a reference. Consumers receive the writer endpoint (the source proxy, or the data member for proxy-free `single`), the cluster CA with `verify-full` (or `verify-ca` where the endpoint name is not in the certificate), the username and the reference. Only the consumer engine driver resolves the password in-process and projects it into that consumer's sealed member configuration. No API read returns it.

### Lifecycle

- **Deletion:** marking a source deleting fails with 409 naming the consumers while bindings exist; the check runs in the same store transaction as the deletion mark, and creating a binding checks the source is not deleting in a serialized transaction.
- **Release:** dropping the consumer releases the binding; its databases and role are dropped on the source only after the consumer's runtimes are gone. A `keepData` release keeps the databases and disables the role.
- **Rotation:** `POST /clusters/{cluster}/postgres/bindings/{binding}/rotate` rotates the role password through the access journal and increments the binding's credential generation. Consumers compare the generation in their reconciliation and roll their configuration; the old password stops working once the source applies the rotation.
- **Version constraints:** a consumer declares the majors it supports. `Ensure` refuses a source outside the range, and the source's major-upgrade admission refuses a target any bound consumer does not support.
- **Shared sources:** several consumers may bind one source. Resolution reports the consumer count. An in-place restore of a source with bindings rolls back every consumer's data; the API requires an explicit acknowledgement flag and the UI lists affected consumers. Acknowledgement is enforced against current bindings in the same writer transaction that admits the restore. Once a restore is pending or running, new bindings are refused with a retryable conflict naming that restore; existing bindings can still be ensured. Admission resumes when the restore becomes terminal. Dedicated sources are recommended for unrelated blast radii.
- **Backups:** consumers may request and observe source backups and in-place restores through an optional binding extension. A consumer requesting its own dedicated-source restore implicitly acknowledges its own binding; any other bound consumer requires explicit acknowledgement, checked in the restore admission transaction.

### Surfaces

`GET /clusters/{cluster}/postgres/bindings` lists inbound bindings on a source (consumer identity, databases, role, credential generation, state). The CLI exposes `karactl postgres bindings list|rotate`; the source detail page shows bindings and restore/upgrade warnings. Consumer engines declare the source in their own `engineOptions`.

### Sample consumer

[Keycloak](https://www.keycloak.org) is the first consumer: a stateless `keycloak` engine driver running the official Keycloak distribution natively on a pinned JDK, configured with one bound database, its bootstrap administrator sealed, and its configuration rolled on credential rotation.

## Consequences

Dependent services share the source's HA, backups, PITR and upgrade path. Source operations now have cross-cluster blast radius that the API and UI make explicit. A source can only be deleted after its consumers. Bindings are limited to sources in the same control plane; external databases remain the consumer's own configuration.

## Alternatives considered

- **Embedded database per consumer:** duplicates lifecycle and resources.
- **Manual roles through the access API:** no rotation propagation, no deletion guard.
- **Superuser or `CREATEDB` consumer roles:** breaks least privilege and isolation between consumers.
- **Arbitrary external user bindings:** the access API already covers application roles; bindings are for managed consumers whose configuration Karakoram can roll.

## Implementation notes

The public binding ID is deterministic for consumer/source identity so cleanup can release a partially provisioned binding. Native ownership is separate: migration 012 persists a random incarnation nonce on insertion, and `kb_<hash>` derives from the binding ID plus that nonce. Creation receipts and request identities follow that native incarnation. No pre-existing bindings exist: this feature is unreleased, migration 012 is edited in place, and no ID or data migration is needed.
