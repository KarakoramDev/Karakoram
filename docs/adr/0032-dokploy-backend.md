# 0032 — Dokploy (Docker Swarm) provider

Status: Accepted; implements [ADR 0030](0030-backend-neutral-infrastructure-contract.md) for a self-hosted [Swarm](https://www.docker.com) managed by [Dokploy](https://dokploy.com)

## Context

Users who operate their own servers asked for a provider other than [Zerops](https://zerops.io). Dokploy is an Apache-2.0 (outside `/proprietary`) platform that runs applications as Docker Swarm services and exposes an `x-api-key` REST API. Swarm offers what Zerops lacks for databases: hard node pinning, so replicas can be kept on distinct hosts. It lacks per-volume quotas, volume growth, source-address filtering for published ports, operation IDs and per-node volume removal through the Dokploy API. Dokploy suffixes every service name with random characters, builds images only on the manager, and needs a registry to distribute images in multi-node Swarms. The tested version is v0.30.8; the API is unversioned.

## Decision

Add a compiled-in `dokploy` factory (`internal/infra/dokploy`), registered next to Zerops. A namespace target is one Dokploy environment; the namespace token is a Dokploy API key.

- **Services.** A runtime is one Dokploy application whose name equals the Karakoram hostname. Member DNS identity is a network alias equal to that hostname on a configurable overlay network, because the Swarm service name carries Dokploy's suffix. A volume is a separate "volume holder" application that is never started: it owns one Docker named volume, a node pin and Karakoram metadata, so it keeps an identity for retention and fenced deletion. Metadata (kind, hostname, mounted volume, node, non-secret variable keys) is stored in the application description; secrets and variables share the Dokploy environment, and only non-secret ownership markers are read back. Secret ownership keys are reported masked.
- **Deployment.** Each deployment uploads an archive with a generated Dockerfile, the release `karakoram` archive, an entrypoint and the non-secret runtime environment. The Dockerfile starts from a digest-pinned [Ubuntu](https://ubuntu.com) 24.04 image, installs the minimal shared packages, runs the engine's unchanged prepare commands as separate cached layers as an unprivileged user with sudo, and adds the artifact. Readiness is validated but not rendered as a Docker health check: Swarm publishes a task's DNS name only once it is healthy, which deadlocks members that must resolve their own name while starting ([Elasticsearch](https://www.elastic.co/elasticsearch) publish host, [RabbitMQ](https://www.rabbitmq.com) node name), and continuous health checks would restart databases on transient unreadiness. A deployment completes when its new task runs; engines check readiness through their agents, as on Zerops. Dokploy builds it on the manager and pushes it to the operator's registry. Services use one replica, stop-first updates and rollbacks, stop-before-delete, a 120 s stop grace period and a raised open-file limit.
- **Placement.** The new neutral `ServiceSpec.SpreadGroup` names an anti-affinity group ([MongoDB](https://www.mongodb.com) replica set, RabbitMQ or Elasticsearch cluster, Elasticsearch masters separately). At import each volume is pinned to the eligible node with the fewest volumes of its group (ties: fewest Karakoram volumes, then name), runtimes inherit the pin, and `Container.PlacementGroup` reports the task's node. Engines treat that value as authoritative when the provider reports `placement`. Member replacement adds the new member before removing the old one, so engines also set `ServiceSpec.SpreadReplaces` to the replaced volume; placement ignores that volume, which lets the new member take its node (the node needs headroom for both during the replacement).
- **Private address family.** `Layout.PrivateAddressFamily` declares whether private service names resolve to IPv6 (Zerops, the default) or IPv4 (Swarm overlays). RabbitMQ selects its [Erlang](https://www.erlang.org) distribution transport (`inet6_*` or `inet_*`) from it; the other engines already listen on dual-stack wildcards.
- **Operations.** Dokploy returns no operation IDs. Operation handles are synthesized, self-describing records (application, previous deployment, previous task IDs, issue time) evaluated against deployment history and task lists, so they survive control-plane restarts. Volume deletion is a durable state machine: refuse while a runtime mounts the volume, run a pinned one-shot wipe task, delete the holder, and remove the Docker volume object when it lives on the manager.
- **Exposure.** Public TCP uses Swarm ingress publishing, so the single target-wide address engines use for status and TLS names reaches every member. There is no source filtering, so `tcpAllowlist` is false; admission now lets an explicitly acknowledged allowlist covering the whole address family pass with only `publicTcp`, and the provider rejects narrower allowlists. Public HTTPS uses Dokploy domains under an operator-supplied wildcard suffix.
- **Target URL restriction.** The Dokploy URL is per-target configuration, unlike the Zerops API URL ([T0 decision in ADR 0030](0030-backend-neutral-infrastructure-contract.md)). It must be a bare origin and is accepted only if it is the operator's `KARAKORAM_DOKPLOY_URL`, listed in `KARAKORAM_DOKPLOY_ALLOWED_URLS`, or — while that list is unset — HTTPS with a DNS name or public IP literal (loopback, private, link-local and shared address literals and `localhost` need an explicit entry). Redirects are never followed and transport errors never contain the URL or key.
- **Capabilities.** `publicTcp`, `placement`, `logs`, `horizontalScaling`, and `publicHttps` when a domain suffix is configured. Not `tcpAllowlist`, `diskGrowth`, `volumeQuota`, `exec`, `metrics`, `scopedTokens`, `dedicatedCpu` or `envChangeRestarts`.
- **Relay and control plane.** Additional Dokploy namespaces use the outbound relay. The control plane can run as a Dokploy application (`deploy/dokploy/Dockerfile`) with a pinned named volume and stop-first updates; its default namespace then reaches members directly over the shared overlay network.

## Consequences

Karakoram can run all current engines on a self-operated Swarm with real host anti-affinity. Docker appears only on this provider, because Dokploy runs Swarm services; members still run the signed `karakoram` binary and the engines' usual package installation.

The operator owns nodes, disks, firewall, registry and Dokploy itself. A node failure leaves its pinned members pending until the node returns or the member is replaced. Volume sizes are not enforced and cannot grow through Karakoram. Public ports have no allowlist and changing them restarts the member. Worker nodes can keep empty Docker volume objects after deletion. API keys are not scoped; a dedicated Dokploy installation is recommended. Dokploy's terms forbid reselling Dokploy as a service without consent; offering Dokploy-backed databases to third parties needs that consent.

## Alternatives considered

- **Docker Engine API directly:** a versioned API without vendor terms, but the credential is root on every node and Karakoram would need its own image build and registry push. Dokploy provides build, registry and domain handling with an API key. A direct Swarm provider remains possible later.
- **Karakoram-built OCI images:** needs an in-process image builder and registry push; prepare commands could not run. A stock image that downloads the artifact at boot needs an artifact server and repeats package installation on every start.
- **Host-mode published ports:** preserve client addresses for firewall filtering, but publish only on the pinned node; engines would need per-service public endpoints for status and certificates.
- **Bind mounts or a Docker-socket cleanup job:** bind sources must already exist on the node and have the same deletion problem; a socket mount gives the job root on the node.
- **Volume as a mount of the runtime:** loses identity and data when the runtime application is deleted, breaking `keepVolumes`.
