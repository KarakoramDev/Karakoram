# 0033 — HashiCorp Nomad provider

Status: Accepted; implements [ADR 0030](0030-backend-neutral-infrastructure-contract.md) for an operator-managed [Nomad](https://developer.hashicorp.com/nomad) cluster

## Context

Nomad offers a self-operated scheduler with native `exec` tasks, ACLs, Variables, native service discovery, dedicated CPU cores and dynamic host volumes. It can run the engines' existing [Ubuntu](https://ubuntu.com) package preparations without [Docker](https://www.docker.com) or installing database packages on the host. Dynamic host volumes require Nomad 1.10 or newer; the tested version is **2.0.7**, not a compatibility guarantee for every release above that feature floor.

The default exec chroot is not a complete package-installation root and can hardlink host files into allocations. Persistent volume claims alone are not a process fence: node-loss reconciliation allowed overlapping allocations in our tests. The built-in `mkdir` host-volume plugin ignores requested capacity. Namespace ACLs authorize the required writes but do not completely isolate metadata in 2.0.7. These observations constrain both the implementation and the advertised capabilities.

## Decision

Add a compiled-in `nomad` factory (`internal/infra/nomad`), registered next to [Zerops](https://zerops.io) and [Dokploy](https://dokploy.com). A target is one existing Nomad namespace **dedicated exclusively to Karakoram, with no other jobs or services**, its credential a Nomad ACL token secret ID. Every native service in that namespace is trusted for hosts generation, so foreign registrations could hijack member names and redirect engine traffic. Runtime import rejects a pre-existing Nomad job without a Karakoram record before creating resources. Operational setup and example policies are in the [Nomad guide](../nomad.md).

- **Identity and records.** Each member runtime is a service job named after its Karakoram hostname. Independently retained runtime/volume identities and desired state live in CAS-protected Nomad Variables at `karakoram/services/<hostname>`, rather than relying on a running job to preserve identity. Environment and secret values live separately at `nomad/jobs/<hostname>`, rendered into the allocation's `secrets/` directory with `change_mode = "noop"`; they apply at the next restart (`envChangeRestarts = false`). Jobs and readable service records do not carry environment values.
- **Exec rootfs.** Dedicated clients use an operator-built Ubuntu 24.04 minbase rootfs containing `ca-certificates`, `sudo`, `curl`, `gnupg`, `util-linux`, `numactl`, uid/gid 10001 and sudoers. The whole root is mapped through client `chroot_env` from a read-only filesystem **different from Nomad's data/allocation filesystem**, forcing private copies rather than hardlinks. The operator builds, patches and versions this image. The client-wide mapping and root username policy belong on a dedicated node pool, not general-purpose exec clients.
- **Privileges and preparation.** Permit root exec tasks on dedicated clients through `user.checked_drivers`, without enabling `raw_exec`. In Nomad 2.0.7, any root exec job on these clients received an unbounded root capability set despite `cap_drop`/`cap_add` and `allow_caps`: every cluster principal whose `submit-job` rights can reach these clients must be trusted, preferably in a dedicated cluster. A node pool is not an ACL boundary and `allow_caps` is not a malicious-root-job mitigation. Karakoram's entrypoint immediately uses `setpriv` to bound its own capabilities to `audit_write,chown,dac_override,fowner,fsetid,setgid,setpcap,setuid,sys_chroot`. It locks any member volume before touching it, waits for self discovery, restores sudo's stripped setuid permission in the private copy, runs ordered preparations as `karakoram` with sudo, installs the artifact, removes its sudoers grant and resets sudo to 0755, then sources secrets and drops to uid/gid 10001. The prepare-only grant is recreated on every start. App and volume roots are `/opt/karakoram` and `/var/lib/karakoram/volumes`; private names use IPv4.
- **Network and discovery.** Use routed [CNI](https://www.cni.dev) bridges with one allocation subnet per node and routes limited to clients, the control plane and authorized LB/proxy sources; allocation listeners are reachable by anything with an allowed route. The CNI chain must invoke `loopback` so every fresh allocation has `lo` up; omitting it broke [RabbitMQ](https://www.rabbitmq.com)'s [Erlang](https://www.erlang.org) distribution startup and is an operator configuration issue, not a reason to grant task `NET_ADMIN`. Allocation IPs allow every member to bind fixed engine ports. CNI supplies reachable external DNS in the bridge plugin. Native services (`provider = "nomad"`, `address_mode = "alloc"`, numeric port 9443) need no declared network port label in the tested 2.0.7 lab; no private/agent host ports are declared. Watched `/etc/hosts` templates query only their own namespace and render every registration, including their own name, with no explicit allocation-IP self line. After bounding and any writer fence, entrypoints poll `getent hosts "$NOMAD_JOB_ID"` every second for up to 120 s before prepare/exec, warning on stderr and continuing if unresolved. `change_mode = "noop"` updates hosts without a task restart. No readiness service check gates discovery during distributed-engine bootstrap.
- **Reboot-safe CNI bookkeeping.** Put host-local IPAM `dataDir` on tmpfs (`/run/cni/networks`), not persistent storage. In the live node-loss test, persistent IPAM state survived a host OOM/reboot and caused restored allocation networking to fail with `duplicate allocation is not allowed`. Clearing ephemeral bookkeeping across reboot is separate from retaining engine host-volume data. Keep the loopback plugin requirement and verify fresh allocation networking after operator changes.
- **Volumes and placement.** Create dynamic host volumes with the built-in `mkdir` plugin, sticky `single-node-single-writer` attachment, and physical names `kk-<first 8 lowercase hex characters of SHA-256(Nomad namespace)>-<hostname>`. At import Karakoram selects an eligible node in the configured pool/datacenters using `SpreadGroup`: fewest volumes of that group, then fewest Karakoram volumes, then stable node ordering. `SpreadReplaces` excludes the predecessor from the group count, permitting replacement on its node when no spare node exists. Runtimes inherit the volume's pin and report the actual Nomad node as authoritative placement. Replacement still needs headroom for both members.
- **Fencing and disconnects.** Deployment/resource/scale/public-port changes explicitly stop the job, wait for terminal allocations, then register the replacement specification. Restart uses that same persisted operation when desired state is running with a saved deployment but no running allocation; Start also recreates dead/absent jobs. Running allocations retain the direct restart endpoint. Members and the separate [SQLite](https://sqlite.org) control-plane job enable unlimited failed-allocation rescheduling with exponential delays from 30 s to 1 h; sticky single-node-single-writer volumes pin replacements to the original node. Unlimited attempts still obey Nomad's 20 minute deployment progress deadline, so a never-healthy deployment can fail and need Start/Restart. After a healthy deployment, subsequent task failures retry without an attempt limit. Volume-bearing groups retain `disconnect.lost_after = "12h"`, `replace = false` and `reconcile = "keep_original"`. A lifetime exclusive `flock`, acquired before preparation/ownership changes and inherited through final execution, serializes writers even if claim reconciliation overlaps allocations. Contenders wait. Stateless jobs may reschedule and spread across nodes. The 120 s task kill timeout requires an operator client `max_kill_timeout` of at least 120 s.
- **Artifacts and operations.** Nomad's artifact mechanism downloads a release archive from the official versioned asset or operator-wide `KARAKORAM_NOMAD_ARTIFACT_URL`. The control plane first verifies that the remote archive contains its exact deployment binary and computes the archive SHA-256, which Nomad verifies during download. Non-release builds require an explicit URL. Durable operation handles plus Variables-backed desired state track evaluations/allocations across control-plane restarts; scheduler task state does not substitute for engine readiness.
- **Pending placement and eventual recovery.** Infeasible/blocked placement evaluations remain pending with diagnostics until the 15 minute startup window, measured from replacement registration, expires. Stop/terminal waiting is not bounded by that window, so a disconnected old allocation cannot leave desired running state permanently stopped through deadline failure. Failure of a registered replacement's operation never deregisters that job or cancels desired running state; Nomad can continue rescheduling within its deployment policy. Service observation prefers a running allocation of the current job version over a failed historical operation. Later Start/Restart/Deploy or changed-port requests supersede that failure through the normal stop/terminal/register fence. Unchanged ports retry only a failed port operation, not an unrelated historical failure.
- **Exposure.** Public TCP reserves static host ports forwarded by CNI `portmap`. Every declared port, including dynamic ports, is forwarded; node firewalls must protect the configured dynamic range (default 20000–32000) and restrict static published ports to LB/proxy sources. There is no routing mesh: an operator LB forwards each advertised public port to the member's actual node, with target public addresses used for status and TLS names. Client source filtering belongs at that LB; provider requests still require the explicit allow-all acknowledgement. The provider does not manage member public HTTPS. The control-plane job defaults `public_port` to 0, omitting host publication; a nonzero value explicitly publishes plaintext HTTP and must be firewalled to the HTTPS proxy/LB only. Direct allocation:8080 proxy access needs the same filtering. The operator supplies HTTPS/WebSocket ingress and private connectivity for 9443.
- **Target policy and TLS.** `address` must be a bare origin approved by `KARAKORAM_NOMAD_ADDR` or `KARAKORAM_NOMAD_ALLOWED_ADDRS`; arbitrary HTTPS to DNS names/public literals is accepted only while both the allowlist and operator client certificate/key settings are unset/empty. Client identity material or an embedding `WithAllowedAddrs` makes the policy restrictive; absent an allowlist, mTLS allows only the operator base origin. Private/loopback/link-local/shared literals and localhost need explicit approval; plain HTTP is explicit-only. Implicit literal checks are not DNS-resolution/rebinding or network-egress protection. API redirects are not followed. CA/client-certificate/key/server-name settings are operator-wide, loaded at factory construction, and cannot be overridden by namespace callers. TLS requires at least 1.2.
- **Capabilities.** Report `publicTcp`, `placement`, `logs`, `dedicatedCpu` (Nomad `cores`) and `horizontalScaling`. Do not report `tcpAllowlist`, `publicHttps`, `diskGrowth`, `volumeQuota`, `scopedTokens`, `exec`, `metrics` or `envChangeRestarts`. Native allocation exec/stats endpoints exist but are not Karakoram provider integrations under ADR 0030. Nomad logs lack per-line timestamps; Karakoram uses the task start time, with whole-run `since` filtering.
- **Relay and control plane.** Additional Nomad namespaces use an outbound relay. The control plane can run as the supplied Nomad job with a node-local, single-writer volume and lifetime lock. It belongs to the default Karakoram target's **Nomad namespace**, so its own native-service template can resolve default-namespace members; routed allocation connectivity provides direct management. An external proxy terminates public HTTPS and forwards WebSocket upgrades.
- **Control-plane least privilege.** The client policy grants exactly `list-jobs`, `read-job`, `submit-job`, `read-logs`, `alloc-lifecycle`, `host-volume-create`, `host-volume-read`, `host-volume-delete`; no filesystem or exec capability. Variables `karakoram/*` and `nomad/jobs/*` allow read/write/list/destroy, with an exact deny for `nomad/jobs/karakoram` to protect control-plane secrets. The job's own workload identity renders those secrets, exporting only `KARAKORAM_*` items and keeping TLS PEMs solely in `secrets/` files. There is no control-plane data-volume mount grant in the client policy: an operator token provisions that volume and registers/updates the control-plane job.

The `host-volume-delete` namespace capability still permits deleting the example's dynamic control-plane volume while unclaimed; omitting a mount grant does not prevent this. A static client-configured host volume on the chosen client, with a node-pinned control-plane job and operator-only mount grant, keeps SQLite/PKI storage outside the dynamic-volume deletion API. The supplied dynamic example assumes a trusted provider token. Listings tolerate undecodable service records, but volume deletion fails closed while one could hide a runtime reference.

## Consequences

Karakoram can run its current engines on a self-operated Nomad cluster without Docker or database packages on the host, with authoritative node placement and dedicated CPU reservations. The operator owns Nomad, client images, filesystem isolation, routes, DNS, firewalls, load balancers and disk monitoring. Nomad Community Edition uses BUSL 1.1 since 1.7; Karakoram does not include or redistribute it, and operators must check HashiCorp's licence terms for their use.

A failed node leaves its data-bearing members pending until recovery or explicit replacement from healthy peers/backups. Single-writer claims and long disconnect tolerance are not enough without the lifetime filesystem lock. Requested disk sizes are metadata, not enforced quotas or reserved capacity. A custom capacity plugin would need a separately supported lifecycle before enabling quota/growth capabilities.

Each new allocation copies a rootfs and repeats engine preparation. In our tests RabbitMQ used approximately 25 s/333 MiB, [PSMDB](https://www.percona.com/mongodb/software/percona-server-for-mongodb) with [PBM](https://docs.percona.com/percona-backup-mongodb/) 100 s/1.6 GiB, and [Elasticsearch](https://www.elastic.co/elasticsearch) 95 s/1.4 GiB, excluding scheduling/artifact/template delays. Task restarts can reuse their allocation's copy and prepare marker. Operators need space for transient extraction, package caches and allocations awaiting garbage collection as well as durable data.

Namespace tokens protect writes, but Nomad 2.0.7 wildcard host-volume listing leaks other namespaces' names/IDs/node IDs/capacities, and workload identities can query cross-namespace native-service metadata. Exact-namespace API requests and templates limit ordinary exposure without fixing the upstream isolation; `scopedTokens` therefore remains false. Node read is cluster-wide and host-volume creation can select a node: a configured node pool is not an ACL security boundary.

## Alternatives considered

- **[Consul](https://developer.hashicorp.com/consul) DNS:** would introduce another service, credential and operational dependency. Nomad native services plus namespace-local watched hosts templates supply engine names, with bounded startup polling for the job's own registration.
- **Static host networking:** avoids allocation routes but makes identical engine ports collide between members on a node, including temporary replacement overlap. Routed allocation IPs preserve engine ports and isolate public host-port reservations.
- **`raw_exec` or host-installed engine packages:** bypasses chroot isolation and couples engine versions, apt state, users and files to the host. Native exec with a private package-capable rootfs preserves the existing runtime preparation contract.
- **Default exec chroot or same-filesystem rootfs:** omits the complete dpkg/apt state needed for preparation and risks hardlink writes to host/source files. Whole-root mapping from a separate read-only filesystem provides a complete, privately copied package base.
- **Docker driver:** viable for a different provider design, but adds an OCI image/build/distribution lifecycle and does not exercise the existing package preparations directly in exec. Docker is not required by this provider.
- **Job as the only service identity:** loses retained identity when a job is purged and cannot represent an independent volume before deployment or after runtime deletion. Variables records preserve `keepVolumes`, desired state and identity-fenced deletion independently of job lifecycle.
- **Relying on sticky single-writer claims alone:** did not prevent overlap after node-loss reconciliation in our tests. Explicit stop/terminal/register sequencing handles normal changes; a lifetime volume lock is still required for the partition/reconnect case.
- **`stop_on_client_after`:** stops otherwise healthy databases during a management-plane partition and cannot be combined with `lost_after` in the tested configuration. Long disconnect tolerance with `replace = false`, original-allocation reconciliation and a filesystem writer fence avoids that deliberate availability loss without trusting claims alone.
