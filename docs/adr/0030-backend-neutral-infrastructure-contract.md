# 0030 — Backend-neutral infrastructure contract

Status: Accepted; generalizes the infrastructure seam in [ADR 0006](0006-zerops-backend-client.md) and backend selection in [ADR 0018](0018-multi-project-namespaces-relay.md)

## Context

The original Backend interface isolated HTTP calls but still exposed Zerops-shaped intent: `ZeropsYAML` deployment documents, platform service-type strings, `/mnt` mount assumptions and Zerops error codes. Namespace registration constructed Zerops clients directly. A second implementation would otherwise need to emulate Zerops rather than implement the infrastructure semantics the engines actually require. Zerops remains the only registered production backend; this decision does not claim another platform is supported.

## Decision

Keep the compiled-in `infra.Backend` interface in `internal/infra/infra.go`, with backend-owned translation and no platform imports in engines, namespace routing or orphan cleanup:

- **Services and volumes:** `ServiceSpec.Kind` distinguishes `KindRuntime` and `KindVolume`; `Base` selects a neutral runtime base (`BaseUbuntu2404` today). Resources, container bounds, secret `Env`, non-sensitive `Vars` and the mounted volume hostname express intent. Observed services and containers use neutral status constants. A volume remains a separate service with its own ID and lifecycle, not merely a runtime attribute: `keepVolumes`, retained-volume recovery and orphan deletion fencing need that identity after the runtime disappears. Docker named volumes and Nomad host volumes also have identities; separate identity is not inherently a Zerops API requirement. `DeleteServiceByID` refuses hostname reuse with `ErrConflict`.
- **Deployment:** `Deployment` pairs an `Artifact` archive with a `RuntimeSpec` in its `Runtime` field (`internal/infra/runtime.go`). The runtime describes the base, ordered prepare commands, non-secret environment, executable arguments, ports, volume, readiness and stop-before-start behavior. Each backend renders its own deployment format. Zerops renders `zerops.yaml` in `internal/infra/zerops/render.go`; output remains byte-identical to the previous documents for the captured baseline cases. Secrets stay in service secrets, not deployment environment values.
- **Runtime layout:** `Layout` supplies `AppDir`, `VolumeRoot` and unprivileged `User`, with `VolumePath` and `DataDir` helpers, and `PrivateAddressFamily` (added with [ADR 0032](0032-dokploy-backend.md); empty means IPv6). Prepare commands run as that user with passwordless sudo available. Engines derive paths and ownership from the layout instead of assuming Zerops paths or users.
- **Operations:** retain non-blocking `Op`/`OpStatus` polling and persisted operation state. `Op.ID` is opaque: a backend may return a platform operation ID or synthesize a handle; callers preserve it unchanged and return the whole `Op` to `OpStatus`. An empty ID means already complete. Request acceptance still does not prove runtime or engine readiness.
- **Errors:** callers use `errors.Is` with `ErrNotFound`, `ErrConflict`, `ErrRejected`, `ErrUnauthorized`, `ErrUnavailable`, `ErrUnsupported` and `ErrResourceChangeCooldown` from `internal/infra/errors.go`. Backends translate platform codes; `RejectedError`, `SafeDetailer` and `SafeDetail` retain bounded diagnostics without exposing arbitrary platform responses.
- **Capabilities:** `Capabilities` declares `PublicTCP`, `TCPAllowlist`, `PublicHTTPS`, `DiskGrowth`, `VolumeQuota`, `Placement`, `Exec`, `Logs`, `Metrics`, `ScopedTokens`, `DedicatedCPU`, `HorizontalScaling` and `EnvChangeRestarts`. These describe optional features, not an alternative to the core service/volume/deploy/lifecycle contract. In `internal/engine/runtime.go`, `RequirePublicTCP` also checks requested allowlist enforcement, `PublicHTTPS` checks both the flag and `SubdomainAccess`, and `RequireDiskGrowth` rejects unsupported growth. Capability metadata alone does not implement command execution, metrics or placement.
- **Construction and namespaces:** `Registry` holds compiled-in `Factory` implementations; `Target` carries kind, target ID, write-only credential and non-secret config. Factories describe themselves through `BackendInfo`, read default configuration, construct clients and validate target identity/credentials. Namespace backend kind and target ID are immutable. Missing kinds in existing records normalize to `zerops`, as does an omitted create kind. The public field remains `projectId` even though it identifies a backend target. `GET /api/v1/backends` exposes registered kinds, capabilities, relay requirements and accepted config keys; namespace responses expose their backend and enabled capabilities.
- **Relay:** `BackendInfo.Relay` determines whether an additional namespace needs an outbound relay. A backend that supplies direct management connectivity can omit it. Zerops reports `Relay: true` and retains the existing relay behavior; `default` remains direct. Zerops was the only factory registered in `internal/server/backends.go` when this decision was taken; [ADR 0032](0032-dokploy-backend.md) adds the experimental Dokploy factory.
- **Conformance:** `internal/infra/fake` supplies a stateful in-memory implementation and `internal/infra/contracttest` supplies the shared `Run` suite. Every backend must pass the suite with an isolated harness, including its capability-dependent cases. Zerops passes through an in-process REST API fixture in `contract_test.go`; `TestLiveContract` provides an environment-gated variant under the `e2e` build tag. Fixture conformance is not evidence of live platform compatibility.

Zerops currently reports public TCP, TCP allowlists, public HTTPS, disk growth, volume quotas, logs, scoped tokens, dedicated CPU and horizontal scaling. It does not report placement, exec, metrics or environment-change restarts. Its factory accepts no per-namespace settings: the Zerops API URL comes only from the operator's `KARAKORAM_ZEROPS_API_URL`, so API callers cannot point the control plane and its stored tokens at another host. The fake is test infrastructure, not a user-selectable backend.

## Consequences

A new backend implements the core interface, neutral status/error mapping, layout, artifact/runtime rendering and a factory, reports capabilities honestly, and passes the shared conformance suite. Public HTTPS additionally implements `SubdomainAccess`. Registration belongs in the server composition root; engine providers keep topology, health and database safety decisions. Backend-specific resource-plan translation, if necessary, belongs in that backend rather than engines.

The cutover implements neutral runtime intent, opaque operation handles and capabilities; it adapts persistent-volume intent by keeping separate typed volume identities. Resource portability is only partial: numeric resource bounds remain, disk growth has an explicit capability/unsupported result, and there is no generic resource-to-plan mapping. These remaining seams are deferred until a backend requires them:

- **Private-address resolution:** member hostnames still serve as private DNS names; there is no backend address resolver.
- **Per-service public endpoints:** public TCP discovery still uses `Project` public IPs plus allocated ports, not a general per-service endpoint result.
- **Ownership labels:** ownership remains non-sensitive environment markers plus recorded service IDs and legacy secret evidence, not a platform-label abstraction.
- **Log fallback:** member logs already come from the node API, while infrastructure `Logs` and its capability describe platform logs. There is no new generic fallback from unsupported platform logs to member logs.

The neutral contract still requires Linux runtime services, the supported Ubuntu base, single-writer persistent-volume semantics and artifact execution. It is not a claim to cover arbitrary schedulers or storage models.

## Alternatives considered

- **One OCI image per release:** adds a registry and image publication/distribution dependency that the signed-binary deployment path does not need. Keep executable archives for now; a backend may wrap the binary in its own base image without changing engine intent.
- **Raw manifests in `RuntimeSpec`:** moves platform coupling into every engine and makes conformance depend on undocumented passthrough behavior. Keep structured runtime intent and backend-owned rendering.
- **Volume only as a runtime attribute:** simpler creation input, but loses the independent identity required for retention and fenced cleanup. Keep the mount reference on the runtime and a separate `KindVolume` service.
- **Kubernetes-style out-of-process plugins:** adds protocol/versioning and operational machinery without a current requirement. Keep compiled-in implementations, consistent with [ADR 0019](0019-multi-engine-seams.md).
